# 开发规范

> 课程要求：代码规范（统一格式化、命名约定、分支模型）、PR 必须 ≥1 人评审、文档规范。
> 本文件是团队协作的**操作性约定**，评审时按此打回。

---

## 一、分支模型

```
main            ← 可交付版本，只接受来自 develop 的合并（打 tag）
 └ develop      ← 集成分支，日常合并目标
    ├ feature/m3-radar-versioning     ← 功能开发（一人一分支）
    ├ feature/web-radar-chart
    ├ fix/sse-auth-context-leak       ← 缺陷修复
    └ hotfix/1.0.1-prod-login         ← 紧急修复（从 main 拉出）
```

| 规则 | 说明 |
|---|---|
| 命名 | `feature/<模块>-<简述>`、`fix/<问题>`、`docs/<主题>`、`hotfix/<版本>` |
| 模块缩写 | `m1`–`m6`、`ai`、`web`、`mcp`、`plat`（对应包名），便于按模块统计贡献 |
| 保护 | `main` 与 `develop` 均需 **CI 全绿 + ≥1 人 approve** 才能合并 |
| 同步 | 每天开始前 `git pull --rebase origin develop`，减少冲突面 |
| 合并 | 功能分支合并到 `develop` 用 `--no-ff`（保留分支痕迹，便于答辩展示协作过程） |

## 二、提交规范（Conventional Commits）

```
<type>(<scope>): <描述>

<可选正文：为什么这么改>
```

| type | 用途 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(m3): 雷达版本化与衰减因子` |
| `fix` | 缺陷修复 | `fix(plat): 修复异步请求导致的鉴权上下文泄漏` |
| `docs` | 文档 | `docs: 补充 MCP 工具契约说明` |
| `test` | 测试 | `test(m3): 补雷达缺失来源重归一化用例` |
| `refactor` | 重构（不改行为） | `refactor(m1): 用户 CRUD 迁移到 MyBatis Mapper` |
| `chore` | 构建/配置 | `chore: 固定 surefire 插件版本` |

- `scope` 用模块缩写 → 便于用 `git log --grep` 统计**个人贡献**（课程「个人贡献」25%）。
- 一次提交只做一件事；不提交编译不过的代码。
- 提交信息中说明 **AI 使用情况**（见 `AI使用公约.md` §5.2）。

## 三、代码规范

### 3.1 命名

| 类型 | 约定 | 示例 |
|---|---|---|
| 包 | 全小写，包名即六步闭环 | `cn.zjnu.a02.m3decision` |
| 类 | UpperCamelCase，名词 | `RadarCalculator` `CareerPathService` |
| 方法 | lowerCamelCase，动词开头 | `createVersion` `calculateAndSave` |
| 常量 | UPPER_SNAKE_CASE | `FORMULA_VERSION` `MAX_DEPTH` |
| 数据库表/列 | 小写下划线 | `competency_radar` `calc_input_json` |
| 布尔字段 | `is_` / `has_` 前缀（Java 侧 `isXxx()`） | `is_ai_generated` → `isAiGenerated()` |

### 3.2 分层职责（**越界即架构缺陷**）

| 层 | 必须做 | 禁止做 |
|---|---|---|
| Controller | 参数接收、调用 Service、组装响应 | 写业务规则、直接调 Mapper |
| Service | 领域规则、事务、状态机、事件发布 | 拼接大模型 HTTP 请求（必须走 `AiChatPort`） |
| Mapper / DAO | 单表实体 CRUD（MyBatis） | 写业务判断 |
| Entity | 数据载体 | 包含业务方法（除 `isDone()` 这类语义判断） |

### 3.3 关键约定

1. **统一响应体**：所有接口返回 `ApiResponse`，不直接返回裸对象。
2. **异常**：业务错误抛 `BizException(ErrorCode)`，由 `GlobalExceptionHandler` 统一转换；
   **绝不把堆栈抛给调用方**（尤其是 AI 工具链）。
3. **事务**：写多张表的方法加 `@Transactional`；只读方法不加。
4. **SQL**：MyBatis XML 中显式列出列名，禁止 `SELECT *`；
   所有参数用 `#{}`（预编译），**禁止 `${}` 拼接**。
5. **AI 相关**：业务侧只能依赖 `AiChatPort`；提示词放 `resources/prompts/*.txt` 并声明版本号。
6. **日志**：用 SLF4J 占位符（`log.info("x={}", v)`），禁止字符串拼接；日志中不打印敏感字段。
7. **格式化**：统一 4 空格缩进、UTF-8、文件末尾保留换行；`.gitignore` 排除构建产物。

## 四、Code Review 规范

### 4.1 评审者做什么

| 检查项 | 说明 |
|---|---|
| 需求对齐 | PR 描述是否关联了需求编号（FR-x.x） |
| 分层合规 | 有没有把业务逻辑写进 Controller，或跨模块直接访问对方 Mapper |
| 安全 | 有没有明文密钥、越权风险、`${}` 拼接 SQL、敏感字段出库 |
| 测试 | 改动核心算法是否补充了单测；CI 是否通过 |
| 可读性 | 命名是否表意，注释是否解释了「为什么」而非「是什么」 |

### 4.2 评审者不做什么

- 不做纯风格挑刺（交给格式化工具）；
- 不要求作者实现超出本次 PR 范围的功能（另开 issue）。

### 4.3 记录留档

每个 PR 需在描述中填写模板全部字段；评审意见用 GitHub Review 留痕。
冲刺结束时把**关键 PR 的评审结论**摘录到 `docs/meetings/` 对应周次记录中（过程表现证据）。

## 五、文档规范

### 5.1 目录结构

```
team-project/docs/
├─ 00-运行与演示指南.md        ← 新成员第一份该读的文档
├─ 01-项目概要.md              ← 课程交付物①
├─ 02-需求与设计.md            ← 课程交付物②
├─ 03-测试文档.md              ← 课程交付物⑤
├─ 04-架构设计.md              ← 技术方案
├─ 05-测试与迭代记录.md        ← 迭代过程留档
├─ 06-企业专项/                ← 竞赛加分材料（非课程必需）
├─ 07-演示视频脚本.md          ← 课程交付物③（视频分镜）
├─ AI使用公约.md               ← 团队规范
├─ AI使用记录.md               ← 课程考核项（15%）
├─ 开发规范.md                 ← 本文件
├─ 开源组件清单.md
├─ 数据库设计.md（可并入 02）
├─ meetings/                   ← 周报 + 例会记录（过程表现 20%）
│  ├─ README.md（模板与要求）
│  ├─ Sprint1-周报.md
│  └─ Sprint1-例会记录.md
├─ 实验报告/                   ← 个人交付（每人 5 份）
└─ 个人总结/                   ← 个人交付（每人 1 份）
```

### 5.2 写作要求

1. 每份文档开头写明**上游依据**与**对应课程要求**；
2. 图用 Mermaid（可版本化、可 diff），不贴不可检索的截图；
3. 数字必须可复现（如「154 节点」要能通过 `/api/kg/stats` 查到）；
4. **未完成的工作如实标注**，不写「已完成」的假状态。

## 六、本地质量门禁（提交前自查）

```powershell
# 必跑（快，< 1 分钟）
mvn -o compile
node tools/charts-test.mjs          # 改前端必跑

# 改了接口必跑（需服务已启动）
node tools/api-contract.mjs

# 改了核心算法/安全相关必跑
java -cp "target/classes;target/test-classes;$(Get-Content target/cp-test.txt -Raw)" cn.zjnu.a02.SelfTestRunner
```

CI（`.github/workflows/ci.yml`）会在 PR 上自动执行上述全部检查。
